*Cue Player - platform-independent JUCE/C++ audio cue player (cues, fades, links, loops, vamps) at ~/Projects/cue-player, GitHub PUBLIC*

Platform-independent audio cue player for theatre/live events, started 2026-07-25.
`~/Projects/simplecue`, GitHub **PUBLIC** (github.com/allansargeant/simplecue), MIT.
Renamed from "Cue Player"/cue-player on 2026-07-25. Internal C++ namespace is still `cp`.
JUCE 8.0.6 via FetchContent + CMake, C++20 — same stack as [zero eq](https://github.com/stoatworks-labs/zero-eq/blob/main/docs/NOTES.md) (`zero-eq`).

Built around four concepts the user specified: **cues** (audio file + in/out points),
**fades** (auto in/out, five curve shapes), **links** (cue-to-cue: auto-continue,
auto-follow, crossfade), plus **loop** and **vamp** (loop a section until released).

**Sub-cues** (user's design): each cue nests into derived sub-cues - Play cue always,
Devamp only when there is a vamp, Fade/Stop always. Standby is a (cue, step) pair where
step -1 = the cue itself; `Cue::firePlayWithCue` (default on) makes firing a cue also fire
its Play sub-cue, and applies to OSC/MIDI/DMX as well as GO. Sequencing lives in
`MainComponent::fireStandbyStep()`, not the engine. Consequence the user accepted: a plain
one-shot cue is now two GOs (cue, then Fade/Stop).

**Phases 1 and 2 complete and pushed.** Phase 1: engine, cue model, `.cueshow` JSON show
file, cue list, inspector, waveform marker editor, device selection, per-cue crosspoint
routing matrix. Phase 2: OSC in/out (fixed address scheme + Companion status feed), MIDI
note/CC/program bindings, MSC, MMC, Art-Net and sACN, outgoing MIDI/OSC messages on any
cue, and a `control` cue type. 304 checks pass (`Tests/EngineTests.cpp` +
`Tests/ControlTests.cpp`); `Tests/e2e/*.py` drive a *running* app over real UDP sockets for
OSC and Art-Net (run by hand, not in CI). CI green on macOS/Linux/Windows.

**v0.3.0 released** (v0.1.0, v0.2.0 before it) with unsigned builds for **5 targets**: macOS universal, Windows x64,
Windows arm64, Linux x64, Linux arm64 (release.yml, triggered by a `v*` tag). Screenshots in
the README are generated by the app itself: `SimpleCue --screenshots <dir>` renders offscreen
via JUCE, so no screen-recording permission is needed - see **screenshot capture** (working-practice note, kept in Claude memory).

Streaming **account settings are global** (app preferences, Settings window); a cue carries
only its playlist uri/name/shuffle/repeat. Project **default fade times** live in the show.

**Not built yet:**
- Phase 3 — streaming provider adapters (Spotify/TIDAL/Apple Music/YouTube Music).
- Disk streaming for very long files (everything is memory-resident today), undo/redo.
- **Run in test environments, never on a live show** (Allan, 2026-08-02) — that is
  what the website's Field-testing chip rests on. No MIDI, lighting or streaming
  *hardware* has ever been connected to it, and no external control path has been
  tested end to end.

**Key constraint the user should not be re-litigated on:** no streaming service will hand a
desktop app decrypted PCM (Widevine DRM; libspotify dead since 2015; Web Playback SDK is
browser-only). So streaming cues are modelled two ways — *local capture* from a loopback
device (BlackHole/VB-Cable/PipeWire sink), which is the only path where our fades and
routing apply, or *remote Connect device* control where fades go through the service's
coarse volume endpoint. Each service needs the user's own registered dev app + client ID;
Spotify Connect control needs Premium.

Design decisions worth keeping: audio is resampled to the device rate **at load time** so
loop/vamp maths is exact integer arithmetic on the audio thread; links are pre-scheduled in
samples (not by a UI timer) so crossfades and auto-follows are sample-accurate.
See the repo's CLAUDE.md for the audio-thread rules. Related: [juce gotchas](https://github.com/stoatworks-labs/fleet-notes/blob/main/notes/reference_juce_gotchas.md).
